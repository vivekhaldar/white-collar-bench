## 1. Purpose and scope

Defines the interface between the Kestrow LMS and the Tinderbox course assistant so Dmitri can build the LMS side
(the "context API") independently of the assistant.

In scope: how the assistant gets course context, how a student or instructor session is opened from inside the LMS,
the fields exchanged, auth, and basic error handling.

Out of scope: model choice, prompt design, the assistant UI, gradebook write-back (not in the pilot), analytics export.

## 2. Flow (synchronous request/response)

1. Student or instructor clicks "Course assistant" in the course navigation.
2. LMS calls `POST /sessions` on the assistant with the launch payload (user, course, role).
3. Assistant validates the token, creates a session, returns `session_id` + launch URL.
4. On session start (and when its cached copy is older than 15 min) the assistant calls
   `GET /courses/{id}/context` on the LMS context API.
5. LMS returns the course context document; assistant answers questions grounded in it.

All calls are synchronous. No push from the LMS in v1; the assistant pulls context when it needs it.
The interface is the same wherever the assistant ends up hosted (hosting option still open).

```
LMS ──POST /sessions──────────────▶ Assistant
LMS ◀──GET /courses/{id}/context── Assistant
```

## 3. Endpoints

### 3.1 `GET /courses/{id}/context` (LMS context API, built by Kestrow)

- `{id}` = LMS course ID (e.g. `KES-2027SP-CHEM110-01`)
- Query params: `include` (comma list: `syllabus,modules,assignments,calendar`; default all)
- Returns `200` + course context document (section 4.1)
- `404` unknown course, `403` course not enrolled in the pilot, `503` LMS degraded

### 3.2 `POST /sessions` (assistant)

- Body: launch payload (section 4.2)
- Returns `201` + `{ "session_id": "...", "launch_url": "...", "expires_at": "..." }`
- `401` bad/expired token, `403` user not in a pilot course, `409` session already open (returns existing)

## 4. Field list

### 4.1 Course context document

| Field | Type | Req | Notes |
|---|---|---|---|
| course_id | string | Y | LMS course ID |
| course_code | string | Y | e.g. CHEM 110 |
| title | string | Y | |
| term | string | Y | e.g. 2027SP |
| instructors | array of {name, email} | Y | display only |
| syllabus_html | string | N | sanitized HTML; max 200 KB |
| modules | array of {module_id, title, position, published} | Y | unpublished modules excluded by the LMS |
| assignments | array of {assignment_id, title, due_at, points, description_html} | Y | due_at ISO 8601, local time |
| calendar | array of {event_id, title, starts_at, ends_at} | N | |
| updated_at | timestamp | Y | used for cache invalidation |

### 4.2 Launch payload (`POST /sessions`)

| Field | Type | Req | Notes |
|---|---|---|---|
| user_sub | string | Y | IdP subject; no student ID number |
| display_name | string | Y | |
| role | enum: student, instructor, ta | Y | from the LMS enrollment |
| course_id | string | Y | must be a pilot course |
| locale | string | N | default en-US |
| return_url | string | Y | where "back to course" goes |

No grades, submissions or student ID numbers cross this interface in v1.

## 5. Auth

- Both directions use OAuth 2.0 bearer tokens issued by the Kestrow IdP.
- LMS → assistant (`POST /sessions`): client-credentials token for the LMS, plus the user's SSO assertion
  passed through in the launch.
- Assistant → LMS (`GET /courses/{id}/context`): client-credentials token for the assistant, scope `courses.read`.
- Client secrets live in a secrets vault, not in config files.
- Tinderbox app registration in the Kestrow IdP requested from Teo (identity & access).

## 6. Non-functional / errors

- Context API p95 < 500 ms for a course with up to 40 modules.
- Assistant caches the context document for 15 min per course; `updated_at` lets it skip a refetch.
- Retries: assistant retries `503` twice with backoff, then answers without fresh context and says so.
- Payload limit 2 MB per context document.
- Request IDs (`X-Request-Id`) on every call, logged on both sides.

## 7. Open questions (for ARB / Dima)

1. Does the LMS expose `assignments.description_html` through the existing API, or does it need a new view?
2. 15-min cache: acceptable to faculty, or do they expect edits to show up instantly?
3. Polling vs push: v1 is pull-only. ARB may have a view.
4. TA role: does the LMS distinguish TA from instructor in the enrollment feed?
5. Rate limits on the context API at peak pilot load (all three courses mid-assignment).

pilot courses; no copies of live course content or enrollments in dev/test.
