## 1. Purpose and scope

Defines the interface between the Kestrow LMS and the Tinderbox course assistant so the LMS side (the "context API")
can be built independently of the assistant.

v2 follows the ARB's review of v1 (1 Mar): the ARB asked for an event-based design instead of the assistant polling the
LMS for course context. In v2 the LMS publishes change events; the assistant subscribes, keeps its own copy of course
context current, and only calls the LMS to fetch a snapshot when it has to.

In scope: course-context events, the snapshot fetch, the session launch, the fields exchanged, auth, error handling.

Out of scope (unchanged from v1): model choice, prompt design, the assistant UI, gradebook write-back (not in the
pilot), analytics export.

## 2. Flow (event-based)

1. The LMS publishes an event whenever something the assistant cares about changes: course content, assignments,
   calendar or enrollment (section 3.1).
2. Events go to the Tinderbox topic on the Kestrow integration bus (per the campus integration standard). The
   assistant (Kettleyard tenant `tinderbox-kes-01`) is the only subscriber in the pilot.
3. On `course.updated` the assistant applies the changed sections to its cached course context. On
   `enrollment.changed` it updates who may open a session in that course.
4. On first start, after a gap in the event sequence, or if its copy is older than 24 h, the assistant fetches a full
   snapshot with `GET /courses/{id}/context` (section 4.2) and resumes from the snapshot's `sequence`.
5. A student or instructor clicks "Course assistant" in the course navigation; the LMS calls `POST /sessions`
   (section 4.3), unchanged in shape from v1 apart from auth (section 5).

```
LMS ──course.updated / enrollment.changed──▶ Kestrow integration bus ──▶ Assistant (subscriber)
LMS ◀──GET /courses/{id}/context (snapshot, on demand)────────────── Assistant
LMS ──POST /sessions──────────────────────────────────────────────▶ Assistant
```

No polling. The 15-minute cache and pull cycle from v1 are gone.

## 3. Field list

### 3.1 Event envelope (all events)

| Field | Type | Req | Notes |
|---|---|---|---|
| event_id | string (UUID) | Y | unique per event; the assistant de-duplicates on it |
| event_type | enum: course.updated, enrollment.changed | Y | |
| course_id | string | Y | LMS course ID, e.g. `KES-2027SP-CHEM110-01` |
| sequence | integer | Y | per-course, strictly increasing; a gap triggers a snapshot fetch |
| occurred_at | timestamp | Y | ISO 8601 with offset |
| schema_version | string | Y | `2.0` for this spec |
| data | object | Y | per event type, below |

### 3.2 `course.updated` data

| Field | Type | Req | Notes |
|---|---|---|---|
| changed | array of enum: syllabus, modules, assignments, calendar, instructors | Y | which sections changed |
| syllabus_html | string | N | present if `syllabus` changed; sanitized HTML, max 200 KB |
| modules | array of {module_id, title, position, published} | N | full list if `modules` changed; unpublished modules excluded by the LMS |
| assignments | array of {assignment_id, title, due_at, points, description_html} | N | full list if `assignments` changed; due_at ISO 8601 |
| calendar | array of {event_id, title, starts_at, ends_at} | N | full list if `calendar` changed |
| instructors | array of {name, email} | N | display only |

Sections are sent whole, not as diffs. Simpler to build and simpler to reason about; the payloads are small.

### 3.3 `enrollment.changed` data

| Field | Type | Req | Notes |
|---|---|---|---|
| user_sub | string | Y | IdP subject; no student ID number |
| role | enum: student, instructor, ta | Y | from the LMS enrollment |
| action | enum: added, removed, role_changed | Y | |
| effective_at | timestamp | Y | |

### 3.4 Course context snapshot (`GET /courses/{id}/context`)

Same fields as the v1 context document (course_id, course_code, title, term, instructors, syllabus_html, modules,
assignments, calendar), plus:

| Field | Type | Req | Notes |
|---|---|---|---|
| sequence | integer | Y | the last event sequence included in the snapshot |
| updated_at | timestamp | Y | kept from v1 |

### 3.5 Launch payload (`POST /sessions`)

| Field | Type | Req | Notes |
|---|---|---|---|
| user_sub | string | Y | IdP subject |
| display_name | string | Y | |
| course_id | string | Y | must be a pilot course |
| locale | string | N | default en-US |
| return_url | string | Y | where "back to course" goes |

`role` is no longer in the launch payload: it comes from the IdP group claims (section 5).

No grades, submissions or student ID numbers cross this interface in v2, same as v1.

## 4. Interfaces

### 4.1 Event publication (LMS → Kestrow integration bus)

- Topic: `tinderbox.kestrow.lms.v2`
- At-least-once delivery. The assistant de-duplicates on `event_id` and orders on `sequence`.
- The LMS publishes within 60 s of the change being saved.
- Retention on the topic: 7 days.

### 4.2 `GET /courses/{id}/context` (LMS context API, built by Kestrow)

- Returns `200` + snapshot (section 3.4)
- `404` unknown course, `403` course not in the pilot, `503` LMS degraded
- Used on first start, on a sequence gap, and as a 24 h safety refresh. Not on every session.

### 4.3 `POST /sessions` (assistant)

- Body: launch payload (section 3.5)
- Returns `201` + `{ "session_id": "...", "launch_url": "...", "expires_at": "..." }`
- `401` bad or expired token, `403` user not in a pilot course or no pilot group claim, `409` session already open
  (returns the existing one)

## 5. Auth

- Users sign in through the Kestrow IdP. The Tinderbox SSO application releases **group claims**; the assistant maps
  them to roles: `tinderbox-pilot-instructor`, `tinderbox-pilot-ta`, `tinderbox-pilot-student`, scoped per course.
  This replaces the role field in the v1 launch payload.
- LMS → event bus: client-credentials token for the LMS publisher, scope `events.publish:tinderbox`.
- Assistant → LMS snapshot fetch: client-credentials token for the assistant, scope `courses.read`.
- LMS → assistant (`POST /sessions`): client-credentials token for the LMS, plus the user's SSO assertion passed
  through in the launch.
- All tokens issued by the Kestrow IdP. Client secrets live in the Kettleyard secrets vault, not in config files or
  chat.

## 6. Non-functional and errors

- Snapshot fetch p95 < 500 ms for a course with up to 40 modules (unchanged).
- Event size limit 1 MB; snapshot limit 2 MB.
- If the bus is unavailable, the LMS buffers events and publishes them in order when it recovers; the assistant
  falls back to the last snapshot and says so in the answer if its context may be stale.
- Request IDs (`X-Request-Id`) on every HTTP call, `event_id` on every event, logged on both sides.

## 7. Test data

Dummy data only outside production. Real student data stays out of the pilot until the security review is complete:
dev, test and the Kettleyard tenant use generated dummy course shells and synthetic rosters for the three pilot
courses. No copies of live course content or enrollments, and no real `user_sub` values, in dev or test events.

## 8. Open questions

1. Does the LMS already emit change hooks we can map to `course.updated`, or does it need a new publisher job?
2. Do instructors expect assignment edits to reach the assistant in under a minute, or is "a few minutes" fine?
3. Should `enrollment.changed` for a TA require an instructor-side flag in the LMS, or is the enrollment role enough?

**Change log (v2 vs v1)**

- Design: request/response polling (v1) replaced by an event-based context API. LMS publishes `course.updated` and
  `enrollment.changed`; the assistant subscribes. (ARB review, 1 Mar.)
- §3 field list: new event envelope and event payloads (3.1-3.3); snapshot gains `sequence` (3.4); `role` removed
  from the launch payload (3.5).
- `GET /courses/{id}/context` kept, but now only for snapshots; the 15-minute pull cache is removed.
- Auth: roles now come from Kestrow IdP group claims instead of the launch payload; new publisher scope for the bus.
- Errors: sequence-gap recovery and bus-outage buffering added.
- v1 open questions 3 (polling vs push) and 4 (TA role) closed by this design; 1, 2 and 5 replaced by section 8.
- v1 (22 Feb): first version. Request/response context API, two endpoints, field list, auth.
- v2 (4 Mar): this version. Supersedes v1.
